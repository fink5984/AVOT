# עיבוד תמונת ספר: סיבוב, הסרת רקע ירוק וחיתוך

כל תמונה שצולמה עוברת בשרת: **תיקון כיוון → זיהוי רקע ירוק → הפרדת הספר → הסרת רקע → חיתוך → שמירה**. הקובץ המקורי אינו משתנה לעולם.

## 1. סיבוב (ברירת מחדל 180°)
- הסיבוב מוגדר **יחסית לחיישן** — לאותו מסגרת שמוצגת בתצוגה החיה. התצוגה החיה מסתובבת בצד התצוגה (טרנספורמציית CSS על שכבת ה-Live View, בלי עיבוד לכל פריים); הקובץ המעובד מסתובב **בפיקסלים** (libvips, מחוץ ל-Event Loop).
- **EXIF Orientation**: הקובץ מתוקן קודם לפי ה-EXIF, ורק *ההפרש* מהסיבוב המבוקש מוחל (`residualRotation`). קובץ שהמצלמה סימנה `Orientation=3` ולכן כבר מסובב 180° לא יסתובב פעמיים. הבדיקה: `test/imaging-pipeline.test.ts` ("EXIF-rotated original is not rotated twice").
- אפשרויות: 0° / 90° / 180° / 270°. חל על התצוגה ועל התמונות המעובדות, נשמר בפרופיל.

## 2. אלגוריתם הפרדה (`apps/web/src/lib/imaging/segment.ts`)
קוד TypeScript טהור, **אותו קוד** בדפדפן (הערכה חיה) ובשרת (עיבוד סופי). ללא OpenCV/ספרייה נייטיבית וללא Docker.
1. **מודל רקע**: HSV; גוון/רוויה נמדדים משולי הפריים (או מדגימת כיול). הסבילות נגזרת מהפיזור הנמדד ומה-slider ״רגישות״ — לא סף קבוע. בהירות רקע: התאמת מישור (תאורה לא אחידה).
2. **ציון חזית רך** לכל פיקסל: סטייה בגוון / ברוויה / בהירות גבוהה מהרקע / כהות עמוקה / מרקם. צל על הירוק (אותו גוון, כהה יותר, עד יחס ~0.45) נשאר רקע; כריכה כהה מאוד נשארת חזית.
3. **Hysteresis** + סגירה/פתיחה מורפולוגית קטנה (≈0.4% מהצלע) → רכיב ראשי בלבד → **מילוי חורים סגורים** (איור ירוק בתוך הכריכה לא נמחק) → הסרת "אי" רעש.
4. **שני שלבים ברזולוציה**: המסכה מחושבת על עותק ≤1200px; בשלב הסופי היא מוגדלת לרזולוציה המקורית וכל פיקסל ברצועה צרה סביב הקו מוכרע מחדש מהצבע שלו (`refineAlpha`), כך שהקצה מדויק לפיקסל במקור. אין הקטנת רזולוציה בתמונה הסופית.
5. **Despill / Decontamination**: הסרת גוון ירוק מקצוות (`g ← min(g,(r+b)/2)` ממושקל לקרבה לקצה ולגוון הרקע) ופירוק ערבוב רקע בפיקסלים חצי-שקופים. אין הילה ירוקה (נבדק).
6. **חיתוך**: מלבן מינימלי סביב אלפא ≥ 50% + שוליים באחוזים. **הסרת רקע וחיתוך הם שתי פעולות נפרדות** (שני מתגים).
7. **פורמט**: ברירת מחדל JPEG (4:4:4, איכות 95) על רקע לבן; PNG שקוף; צבע רקע אחר. אין שינוי רזולוציה.

## 3. בקרת איכות — אין חיתוך הרסני בשקט
`segmentBook` מחזיר `confidence` (0–1) ואזהרות: `BG_NOT_FOUND`, `TOO_SMALL`, `NO_BACKGROUND`, `TOUCHES_FRAME`, `AMBIGUOUS_EDGE`, `SPARSE_SHAPE`, `MULTIPLE_OBJECTS`. מתחת ל-`minConfidence` (0.6):
- נשמר קובץ **מסובב בלבד** (בלי חיתוך/הסרה), מצב `NEEDS_REVIEW`, תג ״לבדיקה״ ברצועה ואזהרה בצפייה;
- המקור שמור תמיד; אפשר לתקן ידנית (סעיף 5).
בתצוגה החיה מוצגת הודעה כשהזיהוי אינו בטוח — לפני הצילום.

## 4. תהליך אחרי הצילום
```
לחיצה → קובץ → Agent: שמירה + SHA-256 → העלאה מאומתת → [שלב א׳, מיד אחרי ההעלאה, במקביל לתשובה] תצוגה מעובדת מהירה
      → [שלב ב׳, job ברקע] עיבוד ברזולוציה מלאה → מוחלף אוטומטית ברצועה
```
- אפשר להמשיך לצלם בזמן עיבוד: תור ההעלאה של ה-Agent וה-job queue (`PROCESS_FINAL`, `FOR UPDATE SKIP LOCKED`) עצמאיים.
- **שיוך**: כל צילום נושא `captureId` ייחודי + ספר + קטגוריה שנקבעו בלחיצה (הטבלה `PhotoAsset` ייחודית ל-`organizationId+captureId`). לא נעשה שימוש בשם קובץ אחרון. נבדק: 20 צילומים ברצף על 3 ספרים (`test/integration/book-processing.it.ts`) ו-6 צילומים עם החלפת קטגוריה (`e2e/digicam-green-screen.spec.ts`).
- **שרידות**: כישלון עיבוד → `FAILED`, המקור והתצוגה הרגילה נשמרים; job שנאבד → תחזוקה מתזמנת מחדש; job ישן לא דורס תיקון ידני חדש (טביעת אצבע של ההגדרות).
- חישוב כבד אינו חוסם את שרת ה-Web: השלבים מופרדים ב-`setImmediate`, והמרות/סיבוב/קידוד רצים ב-libvips.
- **מגבלה ידועה**: הסגמנטציה היא JavaScript על ה-Thread הראשי של שרת ה-Web (תמונה אחת בכל פעם לכל תהליך; תוצאת השלב המהיר נשמרת בזיכרון ונעשה בה שימוש חוזר בשלב המלא). תמונת 4K ≈ 3 שניות CPU בסך הכול. בצילום רציף ממספר עמדות מומלץ שירות Worker נפרד (`JOB_WORKER_ENABLED=false` בשרת ה-Web) או מעבר ל-`worker_threads` (לא מומש).

## 5. תיקון ידני
כפתור ״תיקון חיתוך / רקע״ ברצועת הצילומים (או `POST /api/assets/{id}/process`): שוליים, חיתוך ידני, רגישות, מברשת **מחיקת רקע שנשאר** / **החזרת חלק מהספר**, סיבוב, שקוף↔לבן, שחזור המקור, שמירה. ההערכה על המסך מחושבת באותו אלגוריתם; בשמירה נשלחים רק ההגדרות והסימונים והשרת מעבד מחדש **מהמקור** ברזולוציה מלאה.

## 6. מודל נתונים (`20261026090000_book_processing`)
`PhotoAsset`: `imageState` (`NONE|QUEUED|PREVIEW_READY|DONE|NEEDS_REVIEW|FAILED`), `processing` (snapshot ההגדרות + תיקונים ידניים), `processingResult` (ביטחון, אזהרות, גבולות, זמנים), `processedKey/Mime/Width/Height`. המקור = `PhotoFile` (ללא שינוי), ממוזערת/תצוגה = `thumbKey/previewKey` (מבוססות כברירת מחדל על המעובד). טבלה `CameraProfile` (פרופיל ברירת מחדל אחד לארגון). המיגרציה תוספתית בלבד; Rollback: `prisma/rollback/20261026090000_book_processing.down.sql`.

## 7. פרופילי צילום
ISO / צמצם / תריס / איזון לבן / פוקוס / פורמט (לפי מה שהמצלמה מדווחת) + סיבוב + הסרת רקע + רגישות + שוליים + צבע רקע + מצב תצוגה חיה. נטען אוטומטית בכניסה למסך הצילום, נשמר בשרת אחרי כל שינוי, **לא מתאפס אחרי צילום**. ההגדרות "קופאות" עם הצילום (`PhotoAsset.processing`) ולכן שינוי פרופיל אינו משנה צילומים קיימים.

## 8. ביצועים ומגבלות
- הערכה חיה: עותק של 176–320px, ≤9 פריימים/שנ׳; כשהממוצע חורג מ-70ms מוריד רזולוציה, ואם עדיין איטי עובר למסגרת חיתוך בלבד (העיבוד המלא אחרי הצילום). אין האצת GPU (מיותר ברזולוציה זו).
- זיכרון בשרת: צילום 33MP (R7) מחזיק ≈300MB בשיא; ה-job queue מעבד תמונה אחת בכל פעם לכל מופע.
- **הספים כוילו על תמונות סינתטיות** (כריכה סגורה/פתוחה, קצוות שחוקים, צל, כריכה ירוקה/כהה, תאורה לא אחידה). לא נבדק על ספרים אמיתיים: לפני עבודה שוטפת יש לצלם 20–30 ספרים מייצגים ולבדוק (ראו hardware-acceptance.md §ד). כריכה בגוון זהה לרקע (ירוק באותה רוויה ובהירות) **אינה ניתנת להפרדה בצבע** — מזוהה כ-`TOO_SMALL`/`BG_NOT_FOUND` ומפנה לתיקון ידני.
- לא שולב מודל Segmentation נוסף (ML) — הארכיטקטורה מאפשרת להוסיפו כשלב לפני `hysteresis`; המנגנון הנוכחי + QC + תיקון ידני הוא הבסיס.
